# BP 文档收尾 review — 设计文档

> 主目标：以 `BP02-iron-base.md` 为金本位，对 18 个 Tier 6 蓝图分册（BP01-BP15 + BP-TERM-A/B + BP-BUS-FILLER）做一次性结构 + 引用一致性 review，产出一份诊断报告，用户审阅后批量修复。
>
> 涉及目录：[`docs/superpowers/specs/2026-05-06-tier6-blueprints/`](2026-05-06-tier6-blueprints/)

---

## 背景

最近一系列提交（`722dedc` 起到 `e139211`）把 BP01-BP15 + 3 个工具 BP 的俯视图统一为 BP02 风格（每层独立 ASCII 内容 + Unicode 盒形 ┌─┐│└┘）。但风格统一过程中存在两类潜在问题：

1. **章节缺口与列头偏离**：18 个 BP 分多次提交风格化，难免存在章节漏补、表格列头不齐、个别 BP 没跟上 BP02 最新结构。
2. **belt 引用未双向对齐**：BP02 说「输出铁锭剩余 → BP2b」，BP2b 是否对应声明「输入 ← BP2a」？流量数字两边是否一致？跨蓝图配对覆盖了 18 BP × 任意上下游组合，人脑容易漏。

这次任务的目的是把这两类问题彻底清查，作为 Tier 6 蓝图文档进入实现阶段（写 `data/schemes/*.json`）前的最后一道闸。

## 范围

**包含**：

- 18 个 BP 文件 + README.md（共 19 个 .md）的结构、表格、视觉风格、跨 BP 引用
- 与 README 总表的数据交叉（超频%、Power Shard、集群分类）
- 一次性诊断脚本 + 诊断报告
- 报告确认后按问题类别批量修复 BP 文件

**不包含**：

- `docs/superpowers/specs/2026-05-06-tier6-blueprint-design.md`（主设计文档，本次不动）
- `data/schemes/*.json` 实现（这是下一阶段任务）
- Tier 7+ 扩容蓝图（README 提到的 BP16-BP24，本次不在范围）
- 主设计文档与 BP 分册之间的一致性（仅检查 BP 之间 + BP vs README/index）

## 设计原则

1. **BP02 是金本位但不强制章节列表完全相同**。BP02 因为是 C1 集群锚点（2 实例 a/b 直通），独有「跨蓝图侧墙 mount 配置」「关键同轴对齐」「侧视剖面」三个章节 — 这些章节豁免，不要求其他 BP 也加。
2. **belt 引用配对仅基于结构化数据**。「物料 I/O」表是每个 BP 都有的固定结构（方向/物料/流量/路径），可靠可解析。正文里散落的「← BP1」「→ BP12」太杂乱，归到「补充 cross-link」段落仅展示，不强制配对。
3. **报告先行，确认后改**。脚本输出诊断报告，用户先 review 决定哪些修、修到什么程度，避免脚本自动改文档造成不可控变更。
4. **薄测试**。脚本是一次性诊断工具，单测仅覆盖解析逻辑正确性，不投入集成测试。

## 架构

### 脚本目录布局

```

├─ extract-belt-refs.ts    # 提取「物料 I/O」表中的 belt 引用 + 双向 join

└─ __tests__/
   ├─ md-parse.test.ts

   └─ extract-belt-refs.test.ts
```

## 详细检查项规范

### A. 章节级

#### A1 必备章节存在性

每个 BP 必须含以下 7 个 H2 章节（按出现顺序，但允许中间穿插其他章节）。匹配规则：H2 标题去掉 emphasis 标记后，按下表「匹配关键字」做**包含匹配**（关键字在 H2 文本中即可，括号注释不影响）。

| # | 必备章节 | H2 中包含的关键字 |
|---|---|---|
| 1 | 概要 | `概要` |
| 2 | 机器超频清单 | `超频清单` |
| 3 | 物料 I/O | `物料 I/O` 或 `物料I/O`（容错空格）|
| 4 | 楼层占用 | `楼层占用` |
| 5 | 俯视图 | `俯视图` |
| 6 | 建造步骤 | `建造步骤` |
| 7 | 验证 | `验证`（独立的「验证」章节，不算「验证清单」之类的子标题） |

输出：每 BP 列「缺失章节列表」+「多出的章节」（多出不视为错，仅信息）。

#### A2 章节顺序

A1 的 7 个必备章节必须按上面顺序出现（中间可穿插任意非必备章节）。仅检查相对顺序。

#### A3 BP02 独占章节豁免

以下 BP02 独有章节**不**计入「多出」：

- `## C? 集群完整路由（关键！）`（C1 集群锚点用，BP02 独有；BP06/BP07 等多实例集群锚点也允许）
- `## 集群内部跨蓝图侧墙 mount 配置`（BP02 独有）
- `## 关键同轴对齐`（BP02 独有；其他 BP 内部对齐写在「建造步骤」里即可）
- `## 侧视剖面（east-west...）` / `### 侧视剖面`（BP02 独有；其他 BP 仅俯视图）

报告里把这些豁免章节列在 §A.A3，仅供参考。

### B. 表格级 + 视觉

#### B1 「物料 I/O」表列头一致性

期望列头集合（按 BP02 当前列头为基准）：

```
方向 | 物料 | 流量 | 路径
```

允许扩展（BP02 因 a/b 双实例多 1 列）：

```
方向 | 物料 | 流量 | 路径（BPxa 视角）| 路径（BPxb 视角）
```

报告里列出每 BP 该表的实际列头 + 与基准的差异。

#### B2 「机器超频清单」表列头一致性

期望基准（沿用 BP02 当前格式，待脚本扫一遍后确定具体列名 — 设计阶段不强行硬编码，由脚本第一次跑时**取 BP02 列头**作为基准）。

#### B3 俯视图风格

每个 BP 的「俯视图」章节必须满足：

- 至少有 1 个 H3 子章节匹配 `### NF (高度): 内容`（如 `### 1F (0-8m): ...`）
- ASCII 块中含 Unicode 盒形字符（至少出现 `┌` `┐` `└` `┘` 中任意 1 个）
- 章节标题含「按实际比例」字样

不满足任一条 → §B.B3 记录。

### C. belt 引用配对

只解析「物料 I/O」表内容。表头识别后，逐行：

- **方向列** = `输入` / `输出` / `直通输出` / `直通输入` / `反向直通` / `反向输入` 等含「输入」「输出」的字符串
- **物料列** = 物料名（如「铁锭」「螺丝」）
- **流量列** = 数字 + `/min` 或纯数字（如 `224 给 BP3`）
- **路径列** = 含 `← BPxx` / `→ BPxx` / `BPxx 左 Wall Inlet` 等引用

对每一行提取 `(本BP, 方向, 物料, 流量, 引用 BP)` 五元组。

#### C1 未配对引用

对每条 `(A, 输出, X, N, → B)`，在 B 的表里找 `(B, 输入, X, N, ← A)` 是否存在。
- 找不到 → §C.C1 记 `A → B 物料 X (N/min) 单边声明`
- 找到但流量不同 → 进 C2

也反向检查：对每条 `(A, 输入, X, N, ← B)`，在 B 的表里找 `(B, 输出, X, N, → A)`。

#### C2 流量冲突

C1 的反向：配对成功但两边数字不同。
- 输出：`A → B 物料 X：A 声明 N1，B 声明 N2`

#### C3 表外散落 cross-link

正文中（非表格区域）出现的 `BP\d+` / `BP-TERM-[AB]` / `BP-BUS-FILLER` 引用：
- 仅提取上下文 30 字符
- 列在 §C.C3 段，不参与配对，仅供人工 review 时参考

### D. 数据交叉 vs README

`docs/superpowers/specs/2026-05-06-tier6-blueprints/README.md` 含两个关键表：
- 「蓝图索引」表（C集群、BP编号、当前激活、满载、文件链接）
- 「全厂 T6 Power Shard 总览」表（BP、T6 激活、Power Shard、主要超频配方）

#### D1 超频百分比

对 README「Power Shard 总览」表的「主要超频配方」列，提取 `配方名 N%`，与对应 BP 的「机器超频清单」表对比：

- README 列的每条 `配方名 N%` 在 BP 表里必须能找到（配方名 + 百分比都对得上）→ ✓
- README 列的某条找不到 → §D.D1 记录「README 缺失 / 不一致」
- BP 表里多出的配方（README 没列）**不算偏离**（README 「主要」字面意思是仅列重头戏）

#### D2 Power Shard 总数

README 表的「Power Shard」列 vs BP 「机器超频清单」表底部的 shard 总和。

#### D3 集群分类 (Cx)

每个 BP 文件 H1 标题末尾的 `(Cx)` 必须与 README 「蓝图索引」表的「集群」列一致。

## 异常处理

- **解析失败的文件**：报告新增段 `§E. 无法解析的文件`，列文件名 + 错误，不阻塞其他 BP
- **表格列头未识别**：警告 + 跳过该表，不参与列头一致性比对
- **引用语法无法解析**：归到 §C.C3，仅展示
- **README 表数据缺失**：报告 §D 段标注「README 数据不完整」，跳过涉及该 BP 的数据交叉

## 执行流程

1. **跑脚本**：`npm run bp-review` → 写出报告
2. **人工补充**：我（AI）读报告，在 §F 段写人工视觉风格观察
3. **用户 review 报告**：确认哪些修、按什么顺序修
4. **批量修复**：按问题类别分 commit
   - commit 1: §A 章节级修复
   - commit 2: §B 表格列头 + 俯视图风格修复
   - commit 3: §C belt 引用对齐
   - commit 4: §D 数据交叉对齐
5. **再跑一次脚本验证**：报告应全 ✓
6. **删除一次性诊断报告**（脚本保留作为后续 verify 工具）

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 「物料 I/O」表实际格式比 BP02 多样化（如某 BP 用「源 / 目标」列名） | C1/C2 配对率低 | 第一次跑后 review 报告，针对实际多样性放宽 regex；表头不匹配时降级到 §C.C3 |
| 「机器超频清单」表列头比想象中差异大 | B2 输出冗长 | 不强制完全一致，仅列出与 BP02 不同的 BP |
| 用户 review 时改 BP02 金本位 | 需要重跑 | 设计上脚本支持随时重跑，BP02 当前规则仅是「第一次基准」 |
| README 数据本身就有错（与所有 BP 都不一致） | D 段误报 | §D 报告里同时显示 README 值 + 各 BP 值，让用户判断哪边是真相 |
